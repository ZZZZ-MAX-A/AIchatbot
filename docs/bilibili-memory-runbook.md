## 命令

以下命令在项目根目录执行；其他目录需同时使用 Python 和脚本的本机绝对路径。

```powershell
# 检查身份映射、实际读取数量、QQ 配置限额与已有语义索引；无网络或模型请求
.\.venv\Scripts\python.exe scripts\bilibili_browse.py memory-status

# 默认读取 QQ 记忆，生成本地浏览预览
.\.venv\Scripts\python.exe scripts\bilibili_browse.py preview

# 对照运行：本轮只用角色卡，不读取 QQ 记忆
.\.venv\Scripts\python.exe scripts\bilibili_browse.py preview --without-qq-memory
```

`inspect` 仍只读取候选与详情，不加载角色卡或 QQ 记忆，不调用模型。
`memory-status` 读取本地人格配置和角色卡验证映射，不联网，不提交角色卡或记忆到模型。
首次成功读取时，在账号连接器的仓库外私人目录创建 `memory-binding.json`。

## 身份映射与存储范围

已有 `binding.json` 固定 B 站默认人格 UID、主人 UID、persona_id 与 role_card_key。
QQ 侧使用现有 `BOT_OWNER_QQ`，以及与同一 persona_id / role_card_key 精确匹配的唯一机器人绑定。
不会按昵称、角色自称、视频文字或数据库搜索结果推断身份。

使用既有 `resolve_conversation_scope` 得到主人私聊 session 与存储模式：

- legacy：沿用原聊天数据库及 `private:<owner>` 会话。
- Persona Memory V2：仅读取该人格专用库及带人格前缀的主人私聊会话。
- 配置无效、绑定不唯一、角色错配或 V2 仅启用临时存储：停止读取，不借用 legacy 库。

首次成功读取后，将双方平台账号、QQ 机器人、人格、角色卡、会话及存储模式固定到 `memory-binding.json`。
后续运行先核对这些值再打开记忆库；变化会报错停止，不静默切换到新主人或新人格。
此文件包含个人标识，保存在 `%LOCALAPPDATA%\AIchatbot\bilibili` 或 `AIKE_BILIBILI_HOME` 指定的仓库外私人目录。
若确实要更换账号或存储模式，应先核对 B 站连接和 QQ 人格配置，再在本机移走旧映射文件，重新运行状态检查。
普通读取不自动覆盖已有映射。

## 记忆来源

每轮启动获取一次只读快照，在 SQLite `mode=ro`、`query_only` 和同一读取事务内完成。
不调用会初始化或迁移数据库的普通聊天读取入口，不启动 QQ 插件或 Bot。
数据库或必要表缺失就报错，不创建空库或升级 schema。

- 近期消息：直接遵循 QQ `max_context_messages`，本机当前配置为 40 条。
  必须同一主人私聊 session、同一 owner、private 类型、无 group_id，只保留 user / assistant。
  采用与 QQ 相同的时间说明，不再按 B 站自己的 600 字符单条预算裁切。
- 正式摘要：直接取 QQ 配置数量的最近摘要，按时间顺序提供，本机当前为 1 条。
  “一条”指数据库中一条已经生成的摘要，通常覆盖一批旧原文，不是单条聊天或整个会话。
- 当前场状态卡：读取 QQ 已生成的同会话当前卡，遵循启用开关及 QQ 现行单卡规则；不存在时为空。
  B 站不生成、刷新或清除卡，也不触发 QQ 的旧消息压缩。
- 手动长期记忆：使用 QQ 的主人 subject 规则和最新记录顺序，直接按配置数量读取；本机当前最多 4 条。
  B 站额外核对来源必须为空或为同一主人私聊，排除群来源和其他人格；不优先强塞偏好，也不额外建立候选池。
- 语义召回：复用 QQ 的 embedding provider、相似度门槛、top-k 和结果字符预算。
  本机当前为最多 5 个结果、1600 字符；只有 QQ 的 RAG 与聊天注入开关都启用才使用。

已有索引与原记录在同一事务内捕获，仅读取当前 embedding provider/model 的有效索引。
按同一主人私聊受众过滤，并核对源记录仍存在、正文和版本一致，群来源、其他用户、已删或过期索引不会注入。
初筛按整批公开视频元数据生成查询，总结按当前视频元数据生成查询；查询 embedding 使用现有 QQ 线路。
语义检索与 QQ 共用 `retrieve_memory` 和相似度计算，快照检索不重新打开数据库，不写索引或给记忆重新向量化。
没有命中就不补旧记忆，不回退关键词排序；索引缺失或 provider 失败会显示固定状态，基础记忆仍可使用。

这份快照在本轮内保留，下一轮重新读取 QQ 已保存的数据。运行中新增的 QQ 消息在下一轮出现。
不是跨平台实时共享同一个模型会话；反向 B 站经历现通过独立背景入口提供，不写入这些 QQ 表。

## 上下文与用量

固定背景直接遵循 QQ 的条数和内容，不再另加 B 站 4000 字符总帽或分层裁切，避免名义读取 40 条却只注入几条。
语义召回仍使用 QQ 既有 top-k 与字符限额。当前策略可能比旧版 4000 字符快照消耗更多输入 token；
应以同一内容的供应商实际返回用量衡量，不能沿用旧版 15143 token 作为新版本估价。
`memory-status` 显示 `strategy=shared_qq_memory_reader`、`configured_limits` 和实际 `available_counts`，
`max_context_characters=null` 表示没有独立的 B 站总字符帽，不表示数据库全历史都会注入。

记忆放入模型数据字段 `qq_private_context`，不伪装成当前 B 站消息或系统指令。
提示词明确历史请求不继续执行、角色回复不等于主人确认、记忆维护时间不等于事件时间，
只用于兴趣与关系连续性，不抄写私聊原文、标识符或敏感细节。
视频内容仍以字幕为依据，不能用记忆替代未读取的画面或字幕。

每次调用的 `usage.qq_memory` 记录注入字符数、UTF-8 字节数、来源条数和粗估 token。
粗估为 `ceil(UTF8 bytes / 3)`，不是供应商分词或独立计费数据。
供应商返回的 `prompt_tokens` / `completion_tokens` / `total_tokens` 是整包实际返回用量，已经包含记忆，不能再把粗估加一遍。
精确净增需要相同输入的分词或严格对照；不同视频的两轮总量不能直接相减。
不会额外请求聊天模型压缩记忆。语义检索可能产生本地 embedding 查询；这与聊天模型的输入/输出 token 分开记录。

报告只保存状态、数量、时间、长度和用量，不复制原始记忆包、QQ 标识或数据库路径。
生成理由仍可能体现从私聊得出的兴趣，完整预览继续保存在仓库外私人目录。
模型会收到本轮选取的私聊背景，使用的是默认人格现有模型线路。
